# Implementation Plan: Кнопка «Check» в превью даёт настоящий вердикт

**Branch**: `fix/preview-check-verdict` | **Date**: 2026-08-22 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `specs/041-preview-check-verdict/spec.md`

## Summary

Три правки, ни одна не изобретает нового правила.

Номер задания доезжает до превью — оно перестаёт спрашивать сервер про
`undefined`. Разметка системы уравнений и стереометрии переезжает туда, где
живёт разметка остальных типов, и оба пути — проверка и сдача — начинают
звать одну функцию. Отказ проверки во втором поколении виджетов становится
видимым, как он давно видим в первом.

Отдельно закрывается дыра, которую починка вскрывает: задание с кодом уходит
в просмотровый режим превью, к шести другим типам, которые сохраняют сами
себя.

Эндпоинт `/exercises/{id}/check` не правится вовсе. Он и сегодня судит через
`grade_interactive_detail`; достаточно, чтобы эта функция знала два
недостающих типа.

## Constitution Check

| Принцип | Как соблюдён |
|---|---|
| I. Изоляция арендаторов | Границу не двигаем. `/check` уже читает задание через `get_exercise(db, exercise_id, user)`, а тот проверяет организацию. Превью показывается только своим заданиям. |
| II. Тест, способный упасть | Каждый тест этой правки красный на нынешнем коде, и падение идёт в тело PR. Проверка для `math_system` сегодня отдаёт `passed=false` на верный ответ — тест падает по существу, а не по отсутствию эндпоинта. |
| III. Сервер — единственный судья | Усиливается. Вердикт для двух типов, который на пути проверки не выносился вовсе, теперь выносится сервером по тому же правилу, что и на сдаче. Ключ ответа наружу не идёт: ответ проверки несёт `score`, `passed` и булевы по пунктам. |
| IV. Продукт и документация говорят одно | Подпись под превью («вердикты — по сохранённой версии») сегодня обещает то, чего нет. После правки обещание становится правдой. Текст не трогаем. |
| V. Наименьшая правка | Ни одного нового модуля, ни одного нового класса, ни одной новой строки перевода. Разметка двух типов **переезжает**, а не копируется: обе функции сдачи начинают звать общую и худеют. |

Нарушений нет, раздел Complexity Tracking пуст.

## Решения

### Р1. Общее правило разметки живёт в `grade_interactive_detail`

Разметка `math_system` и `stereometry` сегодня лежит внутри
`_submit_math_system` и `_submit_stereometry` (`backend/app/exercises/service.py`),
вперемешку с записью решения, начислением опыта и замером времени.
Проверочный путь до неё не дотягивается.

Переносим вычисление вердикта в `backend/app/submissions/service.py`, к
разметке остальных типов, двумя ветками в `grade_interactive_detail`. Функции
сдачи оставляют себе только сохранение и зовут ту же функцию за вердиктом.

*Почему не новый модуль:* второго дома для одной функции не нужно —
`grade_interactive_detail` уже и есть «как сервер отмечает ответ», и её
единственные боевые вызовы — ровно два пути, которые должны совпасть:
эндпоинт проверки и `_submit_interactive`.

*Почему не копия ветки в эндпоинт:* две копии правила расходятся, и
расхождение между ними — это и есть чинимый дефект.

*Цена:* `grade_interactive_detail` теперь умеет бросать `BadRequestError`, когда
задание настроено неверно — уравнения не решаются, тело бессмысленно. Раньше
бросали функции сдачи. Класс уже импортирован в этом файле, круговых импортов
не возникает: `app.submissions.service` не знает про `app.exercises.service`.

### Р2. Эндпоинт проверки не меняется

`backend/app/exercises/router.py:316` уже зовёт `grade_interactive_detail`.
Ветка Р1 включает два типа сама собой. Ошибка настроек прорастёт наружу как
400 с той же формулировкой, что и на сдаче.

### Р3. FR-005 закрывается на фронтенде, не на сервере

После Р1 не остаётся ни одного типа, который может дойти до `/check` и не
получить разметки: второе поколение виджетов — шестнадцать типов, все
размечаются; из первого до проверки доходят только `srs_flashcard` и
`word_search`, оба размечаются; остальные либо просмотровые, либо ходят
своим путём.

Серверная стража поэтому охраняла бы недостижимый случай и стоила бы списка
типов рядом с диспетчером — второго списка, который разъедется с первым.
Вместо этого недоступный вердикт ловится там, где учитель его видит: любой
отказ проверки — 400, 422, обрыв сети, тип без правила — показывает готовую
строку `admin.exercisePreview.verdictUnavailable` и вердикта не рисует.
Сценарии US3 закрываются этим целиком.

### Р4. Задание с кодом уходит в просмотр

`code_challenge` отправляет решение прямо на путь сдачи и режима превью не
смотрит (`frontend/src/components/exercises/exercise-renderer.tsx:768`).
Сегодня его спасает отсутствующий номер. Как только номер появится, тестовый
прогон учителя запишет сдачу — прямое нарушение specs/018 FR-005.

Добавляем `code_challenge` в `SELF_PERSISTING_TYPES` — туда, где уже лежат
шесть типов с той же особенностью и с той же надписью «только просмотр».

*Что теряется:* запуск кода в песочнице из превью. Он непишущий и сам по себе
полезен, но чтобы его сохранить, нужно протащить признак превью внутрь
виджета кода и погасить одну кнопку из двух — отдельная работа с отдельной
проверкой. Здесь важнее, чтобы прогон учителя не записался ученику.

## Порядок и зависимости

1. **Красные тесты первыми** (принцип II). Бэкендовый падает на `passed=false`,
   фронтендовый — на `undefined` в адресе.
2. **Р1 до правки номера.** Пока сервер не умеет отмечать два типа, починка
   номера делает хуже: молчание сменяется ложным «неверно».
3. **Р4 до правки номера.** Пока номера нет, задание с кодом безопасно
   случайно; как только номер появится — опасно. Обратный порядок оставляет
   окно, в котором тестовый прогон пишет сдачу.
4. Р3 (видимый отказ) — в любой момент после красного теста.
5. Браузер: система уравнений в проде, тот же `system-SY004`, на котором
   дефект был найден.
