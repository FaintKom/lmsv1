# Quickstart: White-label settings

**Date**: 2026-08-21 · **Spec**: [spec.md](./spec.md) · **Contracts**: [contracts/ui.md](./contracts/ui.md)

Как убедиться, что работа сделана. Каждый сценарий начинается с того, что
показывает поведение **до** правки — принцип II: проверка, которая не может
упасть, хуже отсутствующей.

## Подготовка

```bash
docker compose -f docker-compose.qa.yml up -d --build --wait
```

Учётные данные QA лежат в репозитории намеренно и никогда не совпадают с
продом. Прогон Vitest и Playwright — как обычно:

```bash
cd frontend && npm test
```

```bash
cd frontend && npm run test:e2e
```

## 1. Цвет школы не делает текст нечитаемым (US1)

**Красное до правки:** сегодня `--primary-fg` — константа, и цвет текста не
зависит от фирменного цвета вообще. Проверка на светлом цвете падает.

1. Войти администратором, открыть `/admin/settings`.
2. Задать основной цвет `#facc15`, сохранить.
3. Открыть любую страницу с кнопкой основного действия.

**Ожидается:** надпись на кнопке тёмная. Измерить, а не посмотреть:

```js
getComputedStyle(document.querySelector("[data-brand-cta]")).color
```

Контраст к заливке — не ниже 4.5:1. Повторить с `#0f172a`: надпись становится
светлой.

## 2. Превью работает до сохранения (US2)

1. На `/admin/settings` изменить основной цвет, **не сохраняя**.
2. Образцы перерисовываются немедленно.
3. Уйти со страницы без сохранения, вернуться.

**Ожидается:** школа на прежних цветах. Превью ничего не записало.

Переключить превью в тёмную тему — образцы меняют фон, тема самого приложения
не меняется.

## 3. Второй цвет предлагается и перестаёт следовать (US3)

1. Не трогая второй цвет, сменить основной — второй пересчитался.
2. Выбрать второй цвет вручную.
3. Снова сменить основной.

**Ожидается:** второй остался выбранным. Это тот самый случай, ради которого
существует `secondary_is_custom`, — сравнением цветов его не поймать.

4. Открыть `/admin/analytics` — вторая серия графика идёт вторым цветом.

**Красное до правки:** сегодня `var(--secondary)` не читает ни одна строка,
поэтому проверка «второй цвет виден» падает до правки, а серии графика
нарисованы литеральными `#3b82f6` и `#10b981`.

## 4. Вкладка принадлежит школе (US4)

1. Задать название и значок вкладки, сохранить.
2. Открыть любую страницу и прочитать `document.title`.

**Ожидается:** начинается с названия школы. Перезагрузить и убедиться, что
«GrassLMS» не мелькает в первом кадре — значение читается до отрисовки, как это
уже сделано с темой.

## 5. Вход через страницу школы (US5)

1. Выйти. Открыть `/login?s=<слаг школы>`.

**Ожидается:** логотип и цвета школы до ввода первого символа.

2. Войти, выйти, открыть `/login` без параметра.

**Ожидается:** бренд той же школы — слаг запомнился.

3. Открыть `/login?s=nonexistent-school`.

**Ожидается:** нейтральный экран. Ответ сервера **не отличается** от ответа для
отключённой школы: 404 в обоих случаях.

4. Проверить `/cookies`: в таблице есть строка `school-slug`.

**Это часть работы, а не документация о ней.** Запись на устройстве без строки в
таблице — расхождение продукта и его документов (принцип IV).

## 6. Публичная страница заявки (US6)

1. Открыть `/s/<слаг>/enquire` **не входя**.

**Ожидается:** логотип, название и цвета школы.

2. Отправить заявку.

**Ожидается:** заявка принята ровно как прежде — оформление ничего не изменило.

3. Убедиться, что публичный ответ не отдаёт лишнего:

```bash
curl -s http://localhost:8000/api/v1/crm/public/qa-school | jq '.branding | keys'
```

**Ожидается:** внутри `branding` ровно четыре ключа. Контакта поддержки, состава
меню и значка вкладки там нет.

## 7. Поддержка ведёт в школу (US7)

1. Задать почту поддержки, сохранить, открыть меню.

**Ожидается:** «Поддержка» ведёт на `mailto:`.

2. Очистить поле, сохранить.

**Ожидается:** ведёт на `/support` — маршрут никуда не делся.

3. Попробовать сохранить `example.school/help` без схемы.

**Ожидается:** отказ с объяснением, а не тихое сохранение адреса, который никуда
не ведёт.

## Изоляция арендаторов

Открывается **положительным контролем** — иначе проверка зеленеет на
несуществующем экране (этот урок оплачен в spec 033).

1. Суперадмином открыть `/admin/organizations/<чужая школа>` и изменить её цвет.
   **Ожидается:** сохраняется. Экран существует и работает.
2. Убедиться, что оформление собственного сеанса суперадмина не поменялось
   (FR-004).
3. Администратором школы обратиться к настройкам чужой школы по её
   идентификатору. **Ожидается:** 404, не 403.

## Школа без настроек

Прогнать существующий обход тёмной темы и снимки экранов на организации, у
которой не задано ничего.

**Ожидается:** ни одного отличия от нынешнего продукта (FR-034). Это самая
скучная проверка здесь и единственная, которая ловит случай «вывели цвет там,
где школа его не задавала».

## Мера предосторожности при проверке в браузере

Переходы, анимации и всё, что живёт на кадрах, **нельзя мерить в фоновой
вкладке**: Chrome там не выдаёт кадры, переход застывает на начальном значении,
и это читается как поломка вёрстки. Первой строкой любой такой проверки —
`document.visibilityState`. Ошибка уже стоила ложного диагноза по проду
2026-08-21.
