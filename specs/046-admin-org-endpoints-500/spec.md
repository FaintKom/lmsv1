# Создание и удаление школы отвечают 500

**Дата**: 2026-08-22 · **Ветка**: `claude/sentry-error-prod-6gq12x` · **Статус**: разобрано

## Что происходит

Оба действия суперадминистратора над школами отказывают в проде. Sentry прислал
их в одну минуту, 22:41 и 22:42 UTC, — кто-то открыл экран управления школами и
попробовал обе кнопки.

```
DELETE /api/v1/admin/organizations/{id}
asyncpg.exceptions.NotNullViolationError:
null value in column "org_id" of relation "users" violates not-null constraint
[SQL: UPDATE users SET org_id=$1::UUID, updated_at=now() WHERE users.id = $2::UUID]
[parameters: ... 16 bound parameter sets ...]
  transaction = app.admin.router.delete_organization_endpoint
```

```
POST /api/v1/admin/organizations
ModuleNotFoundError: No module named 'python_slugify'
```

Причины разные, общего между ними — только экран.

## Удаление: ORM отменяет каскад, который база готова выполнить

Внешний ключ объявлен с каскадом, и не он один: все 33 внешних ключа на
`organizations.id` в кодовой базе несут `ondelete="CASCADE"`. База умеет унести
школу вместе со всем, что ей принадлежит.

До базы не доходит. `Organization.users` — единственная связь ORM, ведущая от
школы к её детям, и объявлена она была без `passive_deletes`:

```python
users: Mapped[list["User"]] = relationship(back_populates="organization")
```

Умолчание SQLAlchemy при `db.delete(org)` — не «удалить детей» и не «отдать
базе», а **отвязать**: подгрузить коллекцию и записать в каждой строке
`org_id = NULL` до того, как уйдёт `DELETE`. Отсюда `UPDATE` в стектрейсе.
Отвязка требует, чтобы колонка допускала NULL, а `users.org_id` объявлена
`nullable=False`. Postgres отказывает, и до `DELETE FROM organizations` дело не
доходит.

Другие 32 таблицы SQLAlchemy не трогает — связи от `Organization` к ним нет, и
их каскад отработал бы штатно. Ломает единственная связь, которая есть.

## Создание: имя дистрибутива вместо имени модуля

```python
from python_slugify import slugify
```

Пакет на PyPI называется `python-slugify`, а модуль, который он ставит, —
`slugify`. Два других места в бэкенде импортируют верно
(`app/auth/service.py`, `app/courses/service.py`); ошибается только это.

Импорт стоял внутри тела функции, поэтому промах не проявлялся ни при сборке
образа, ни при старте контейнера, ни при импорте роутера в тестах, — только на
первой попытке завести школу. Он же стоял первой строкой функции, до проверки
имени, так что и ответ 400 на пустое имя был недостижим: пустое имя тоже давало
500.

## Почему прогон оставался зелёным

`test_super_admin_can_delete_org` существовал и проходил. Школа в нём —
фикстура `org2`, в которой нет ни одного человека: коллекция `users` пуста,
отвязывать нечего, `DELETE` уходит в базу. Тест доказывал, что удаляется
пустая школа. Суперадминистратор удаляет не пустую.

У `POST /organizations` тестов не было вовсе.

## Требования

- **FR-001.** Удаление школы, в которой есть люди, отвечает 200, а люди
  удаляются вместе с ней. Это и есть намерение, под которое база размечена:
  каскад объявлен на всех 33 внешних ключах.
- **FR-002.** Удаление отдаётся базе, а не воспроизводится в ORM перечислением
  дочерних таблиц. Перечисление разошлось бы с базой на первой же новой
  таблице с `org_id`.
- **FR-003.** Создание школы отвечает 200 и возвращает slug, выведенный из
  имени; при совпадении имён slug остаётся уникальным.
- **FR-004.** Пустое имя отвечает 400, а не 500.
- **FR-005.** Импорт, от которого зависит обработчик, разрешается при импорте
  модуля. Промах в имени модуля должен ронять прогон, а не первый запрос в
  проде.
- **FR-006.** У каждого требования есть тест, который падает на неисправленном
  коде.

## Что осталось незакрытым — намеренно

**Удаление школы по-прежнему не спрашивает подтверждения** и не сообщает, скольких
людей уносит. Endpoint защищён ролью `super_admin` и отказом удалять
собственную школу; всё остальное — вопрос интерфейса, а не этой поломки.

**Каскад в проде прочитан по коду, а не по базе.** Все 33 таблицы с `org_id`
объявляют `ondelete="CASCADE"` в моделях, и миграция `d5e6f7a8b9c0` отдельно
выставила его одиннадцати таблицам, которые появились раньше объявления. Но
сами ограничения прода этой правкой не читались — из среды, где она делалась,
до базы нет доступа. `NotNullViolationError` приходил на отвязке, то есть
`DELETE` до базы вообще не доходил, и ни одного каскада прод пока не исполнял.
Если где-то ограничение всё же без каскада, следующая попытка удаления даст
`ForeignKeyViolationError` вместо 200 — и назовёт таблицу. Сверить до мержа
одной командой:

```sql
SELECT conrelid::regclass AS tbl, conname, confdeltype
FROM pg_constraint
WHERE contype = 'f'
  AND confrelid = 'organizations'::regclass
  AND confdeltype <> 'c';
```

Пустой ответ — каскад полный.

**Прочие связи ORM с `passive_deletes` не сверялись.** Правится связь, которая
падала. Сплошная сверка всех связей проекта на расхождение с `ondelete` —
отдельная работа, и её стоит делать проверкой, а не глазами.

## Как проверено

1. **Обе поломки воспроизведены тестом до правки.** Четыре из пяти новых
   тестов падают на неисправленном коде; `UPDATE users SET org_id=$1::UUID` в
   выводе прогона совпадает с тем, что пришло из прода.
2. **Пятый тест — на 403 для обычного администратора — проходил и до правки.**
   Роль отсекает запрос раньше импорта, и это верно.
3. **Прогон бэкенда целиком** на Postgres 16 с `pgvector`, плюс `ruff check`,
   который гоняет CI.
