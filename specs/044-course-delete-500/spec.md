# Удаление курса отвечает 500, когда в уроке стоит задание

**Дата**: 2026-08-22 · **Ветка**: `claude/keen-faraday-3cf9a5` · **Статус**: разобрано

## Что происходит

`DELETE /api/v1/courses/{id}` отвечает `500 {"detail":"Internal server error"}`.
Условие одно: в уроке этого курса стоит хотя бы одно задание. Курс из модуля и
урока без заданий удаляется штатно — проверено на стенде, 200.

Тело ответа общее, поэтому исключение взято из журнала бэкенда:

```
sqlalchemy.exc.IntegrityError: NotNullViolationError:
null value in column "lesson_id" of relation "exercises" violates not-null constraint
[SQL: UPDATE exercises SET lesson_id=$1::UUID, updated_at=now() WHERE exercises.id = $2::UUID]
[parameters: (None, UUID('71d88759-b438-469e-a581-1ff7874030ec'))]
  File "/app/app/courses/service.py", line 371, in delete_course
    await db.commit()
```

## Почему UPDATE, а не DELETE

`specs/030` сделало задание собственностью школы, а не урока: оно заводится в
библиотеке до постановки и остаётся после того, как урок убрали. Поэтому
`Lesson.exercises` объявлено без каскада — намеренно, там об этом комментарий.

Отсюда и `UPDATE`. Удаление курса идёт по ORM: курс → модули → уроки, а на
уроке SQLAlchemy отвязывает задания, то есть пишет `exercises.lesson_id = NULL`.
Задание переживает свой урок — ровно то, ради чего `specs/030` и делалось.

Отвязка требует, чтобы колонка допускала NULL.

## Где расходятся база и модель

|                   | `lesson_id` | FK `ondelete` |
| ----------------- | ----------- | ------------- |
| модель            | nullable    | `SET NULL`    |
| прод              | nullable    | `SET NULL`    |
| поднятый QA-стенд | `NOT NULL`  | `CASCADE`     |

У стенда — форма, которая была до `specs/030`. При этом обе базы помечены одной
ревизией alembic, `m3nukeycl3an`. То есть стенд объявляет ревизию, которой его
схема не отвечает.

## Администратор этого не видит

Прод прочитан напрямую: `lesson_id` nullable, внешний ключ `SET NULL`, ревизия
`m3nukeycl3an`. Форма правильная. Школа, удаляющая курс через интерфейс, эту
ошибку не получает. Сломан стенд, а не продукт.

Проверены оба пути, которыми в этом проекте появляется схема, — и оба дают
правильную форму:

- **Пустая база.** `_run_setup` строит таблицы `create_all` по моделям и ставит
  штамп head. Прогнано на отдельной базе: nullable, `SET NULL`.
- **Существующая база.** `alembic upgrade head`. Миграция `z3a4b5c6d7e8`
  проиграна на отдельной базе, приведённой к старой форме и помеченной
  `dr0pm33t1ng5`: снимает `NOT NULL`, пересоздаёт внешний ключ как `SET NULL`.

Значит ни модель, ни миграция не виноваты, и чинить в них нечего.

Как именно эта конкретная база разошлась со своим штампом, восстановить нельзя:
данные стенда лежат в tmpfs, стенд общий на две сессии, и за девять часов его
поднимали и пересобирали не один раз. Лечение — поднять стенд заново с
`--build`. Это та же семья отказов, о которой предупреждает шапка
`docker-compose.qa.yml`: устаревший образ и молчаливое расхождение.

## Почему это дожило до сегодня

Teardown глотает. В тринадцати спеках стоит один и тот же кусок:

```ts
try {
  await teacherApi.deleteCourse(courseId);
} catch (e) {
  console.warn(`teardown deleteCourse failed: ${(e as Error).message}`);
}
```

Прогон, в котором каждый тест зелёный, печатает предупреждение и заканчивается
успехом. Признак того, что стенд отвечает 500, есть — и не значит ничего.

Хуже, что покрытие у этого случая есть, и правильное:
`test_an_exercise_in_two_courses_survives_deleting_one` удаляет курс, в уроке
которого стоит задание, и ждёт 200. В CI он зелёный — база pytest собирается
`create_all` по нынешним моделям, и форма там правильная. Проверка верна и
смотрит не на ту базу. Единственным, кто видел эту 500, был teardown.

## Требования

- **FR-001.** Уборка, получившая 5xx на удалении курса, валит прогон. Стенд,
  который отвечает 500, не может закончиться зелёным.
- **FR-002.** Прочие отказы уборки остаются предупреждением: курс уже удалён,
  сеть моргнула. База стенда всё равно выбрасывается, и уборка на ней — не
  предмет проверки.
- **FR-003.** Различение живёт в одном месте. Сегодня `catch` скопирован в
  тринадцать спеков; правка, сделанная в тринадцати местах, в тринадцати местах
  и разойдётся.
- **FR-004.** Различение опирается на код ответа, а не на текст ошибки: в текст
  подставляется тело ответа сервера, и «500» может прийти оттуда.
- **FR-005.** Бэкенд не меняется. `delete_course` на правильной схеме ведёт себя
  верно, и это уже покрыто тестом.

## Что осталось незакрытым — намеренно

**Сторожа схемы нет.** Ничто не сверяет схему поднятого стенда с ревизией,
которой он помечен. Заводить такую сверку сейчас не за чем: FR-001 превращает
ровно этот отказ в красный прогон, а причина расхождения — устаревший образ, о
чём в `docker-compose.qa.yml` уже написано. Завести, если дрейф повторится на
стенде, поднятом с `--build`.

**`delete_course` коммитит руками.** `await db.commit()` в сервисе, тогда как
`delete_module` и `delete_lesson` ограничиваются `flush()`, а `get_db` коммитит
сам на успехе. Расхождение с конвенцией проекта, но наблюдаемого эффекта нет:
исключение всё равно поднимается на коммите и всё равно становится 500. Не
трогается этой правкой.

## Как проверено

1. **Поломка воспроизведена по шагам.** Курс → модуль → урок → задание в этом
   уроке, затем `DELETE /courses/{id}` → 500. Тот же курс без задания
   удаляется с 200; после удаления одного задания курс удаляется с 200. Строка
   об исключении сверена с журналом бэкенда по идентификатору курса.
2. **Прод прочитан** — только чтением: `attnotnull` и `confdeltype` для
   `exercises.lesson_id` плюс `alembic_version`.
3. **Оба пути схемы прогнаны на отдельной базе** (`create_all`; и `upgrade` с
   `dr0pm33t1ng5`), база после проверки удалена.
