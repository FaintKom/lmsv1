# Tasks: Six menu items a school cannot switch off

**Input**: Design documents from `specs/040-menu-visibility-controls/`

**Prerequisites**: [plan.md](./plan.md), [spec.md](./spec.md), [research.md](./research.md), [data-model.md](./data-model.md), [contracts/ui.md](./contracts/ui.md), [quickstart.md](./quickstart.md)

**Tests**: обязательны. Принцип II конституции: каждая проверка сначала
демонстрируется падающей против нынешнего поведения, и это указывается в теле PR.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: можно вести параллельно — другие файлы, нет незавершённых зависимостей
- **[Story]**: US1…US5 из спеки

## Что нельзя забыть ни в одной задаче

- Новый `.tsx` обязан звать `useTranslation()`, иначе падает
  `no-hardcoded-strings.test.ts`.
- Каждый новый ключ — во **все шесть** локалей (`en, es, ru, tr, de, uk`) в той
  же правке, иначе падает `translations.test.ts`.
- Токены Lively. Своей эстетики не изобретать.
- Проверка в браузере **начинается** с чтения `document.visibilityState`.

## Phase 2: Foundational — список и проверки на расхождение

**Порядок внутри фазы строгий.** Проверка Б пишется и показывается красной
**до** правки `nav-tree.ts`. Если написать её после, она позеленеет вместе с
правкой и не докажет ничего.

- [ ] T003 Создать `frontend/src/components/layout/menu-items.ts` — единственный упорядоченный список того, что школа вправе скрыть: `{ key, labelKey, group, adminOnly }`, шестнадцать записей по таблице в `data-model.md`. `labelKey` указывает на строки меню (`nav.*`), своих строк список не заводит.
- [ ] T004 Написать проверку **А** в `frontend/src/components/layout/menu-items.test.ts`: для каждого ключа построить дерево со всеми включёнными, затем выключить только этот — исчезает ровно один пункт. Ловит ключ, который дерево не спрашивает.
- [ ] T005 Написать проверку **Б** там же: выключить **все** ключи списка; остаться должны ровно пункты без ключа — сводка, лист ожидания, организации, интеграции. **Прогнать и показать красной**: сегодня останутся ещё шесть. Это та проверка, которой не хватало — разрыв жил месяцами невидимым.
- [ ] T006 Расширить обе проверки на каждую роль со своим меню: администратор, учитель, ученик, родитель. Для ученика и родителя они красные по другой причине — `visible()` там не вызывается вовсе.

**Checkpoint**: список есть, обе проверки написаны и обе красные.

## Phase 3: User Story 5 — выключенный пункт исчезает и у ученика (P1) 🎯

**Goal**: карта видимости применяется ко всем ролям, а не только к персоналу

**Independent Test**: выключить «Командные проекты», открыть продукт учеником — пункта нет; открыть адрес страницы напрямую — страница работает

**Почему первой.** Без неё шесть новых переключателей сделали бы ложь глубже:
школа увидела бы, как пункт исчез у неё, и осталась бы уверена, что ученики его
не видят.

- [ ] T007 [US5] Написать падающие проверки в `frontend/src/components/layout/nav-tree.test.ts`: ученик не видит выключенный пункт; родитель не видит выключенный пункт; пункт без ключа у обоих остаётся. Красные: `visible()` в этих ветках не вызывается.
- [ ] T008 [US5] Провести `visible()` в ветки ученика и родителя в `frontend/src/components/layout/nav-tree.ts`. Шесть пунктов ученика имеют ключ: `courses`, `assignments`, `calendar`, `live`, `peer_review`, `team_projects`. Остальные — `dashboard`, `achievements`, `attendance`, `schedule` — ключа не имеют и не трогаются.
- [ ] T009 [US5] Прогнать T005 и T006 заново: проверка Б обязана позеленеть, потому что лишних пунктов не осталось.
- [ ] T010 [US5] Убедиться, что права не изменились: страница выключенного пункта открывается по адресу тому, кому была разрешена (FR-013). Выключен пункт меню, а не доступ.

**Checkpoint**: карта работает во всех ролях, обе проверки на расхождение зелёные.

## Phase 5: User Story 2 — прежние решения школы не тронуты (P1)

**Goal**: школа, настраивавшая меню раньше, ничего не теряет

**Independent Test**: загрузить форму школы с двумя выключенными пунктами, сохранить не тронув ничего, сверить карту с исходной

**Самая незаметная проверка и самая важная.**

- [ ] T014 [US2] Написать падающую проверку в `frontend/src/components/admin/menu-visibility-section.test.tsx`: карта из десяти ключей, два выключены — на экране выключены ровно эти два, шесть новых включены.
- [ ] T015 [US2] Написать падающую проверку «сохранение без единого изменения не меняет карту» в тесте формы: загрузить карту с двумя выключенными, отправить форму, не тронув переключателей, сверить отправленную карту с загруженной. **Красная против наивной реализации**, которая собирает карту «все шестнадцать включены» и молча включает обратно то, что школа выключала.
- [ ] T016 [US2] Убедиться, что форма собирает карту **из загруженных значений**, а не из умолчаний списка (`contracts/ui.md` §5).

- **Phase 1** → **Phase 2**: список блокирует всё
- **Внутри Phase 2 порядок строгий**: T005 (проверка Б) пишется и краснеет до T008
- **Phase 3 (US5)** и **Phase 4 (US1)**: параллельны — разные файлы
- **Phase 5 (US2)**, **Phase 6 (US3)**, **Phase 7 (US4)**: после Phase 4, строго по
  порядку — все правят `menu-visibility-section.tsx`

### Узкие места

`menu-items.ts` — общий для меню и формы, идёт первым и один.
`nav-tree.ts` — US5 целиком в нём, распараллеливать нельзя.
`menu-visibility-section.tsx` — общий для US1, US3, US4; эти истории идут подряд.

### Parallel Opportunities

- T011 и T012 внутри US1, параллельно всей Phase 3
- Ничего больше: остальные истории делят по одному файлу

## Implementation Strategy

### MVP

Phase 1 → Phase 2 → Phase 3. На этом «выключить пункт» начинает означать то, что
написано на переключателе, — даже до того, как переключателей станет
шестнадцать.

### Инкрементально

1. Setup + список + две проверки → расхождение поймано и видно
2. US5 → карта применяется ко всем ролям
3. US1 → шестнадцать переключателей
4. US2 → чужие настройки не переписываются
5. US3, US4 → читаемость и предупреждение
6. Сохранность → PR
