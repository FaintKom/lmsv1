# Ответ на викторину отвечает 500

**Дата**: 2026-08-23 · **Ветка**: `fix/quiz-submit-answers-500` · **Статус**: разобрано

## Что происходит

Ученик проходит викторину, отвечает верно на последний вопрос — и получает 500.
Работа не сохраняется. Sentry прислал это дважды, 13:00 и 13:06 UTC: два письма,
одно событие, снятое с двух сторон.

```
POST /api/v1/exercises/{id}/submit
TypeError: 'NoneType' object is not iterable
  app/exercises/service.py:837  score_percent, _ = grade_quiz(questions, answers)
  app/assessments/grading.py:126  answer_map = {str(a.get("question_id")): a for a in answers}
  transaction = app.exercises.router.submit_exercise_endpoint
```

`answers` пришёл пустым не в смысле «список без элементов», а `None`.

## Клиент и сервер разошлись в имени конверта

Обёртка V2-рендерера кладёт полезную нагрузку любого типа в один конверт —
[`v2-exercise-live.tsx:167`](../../frontend/src/components/exercises/v2-exercise-live.tsx):

```ts
apiClient.post(`/exercises/${exercise.id}/submit`, {
  interactive_answers: answers,
  elapsed_seconds: timerRef.current.elapsedSeconds(),
});
```

Викторина передаёт туда `{answers: [...]}`
([`quiz-v2.tsx:196`](../../frontend/src/components/exercises/v2/quiz-v2.tsx)). На
проводе получается `{"interactive_answers": {"answers": [...]}}`.

Сервер для типа `quiz` читал верхний уровень:

```python
answers = data.get("answers", [])
```

Ключ `answers` в теле **есть** — схема объявляет его `list[dict] | None = None`,
и `model_dump()` кладёт его всегда, со значением `None`. Умолчание `[]` во втором
аргументе `.get` срабатывает только на отсутствующем ключе, а он не отсутствует.
Отсюда `None` вместо списка и разбор `None` в цикле.

Соседний маршрут этот конверт разворачивал с самого начала —
[`router.py:293`](../../backend/app/exercises/router.py), обработчик `/check`:

```python
answers = data.interactive_answers.get("answers") or []
```

То есть форму никто не менял. Два маршрута читали одно тело по отдельности, и
`/submit` остался на форме, которой клиент не шлёт.

## Почему это не заметили раньше

`onGrade` вызывается не на каждый ответ, а только когда верно отвечен
**последний** вопрос
([`quiz-v2.tsx:203`](../../frontend/src/components/exercises/v2/quiz-v2.tsx)).
До этого момента викторина ходит в `/check`, который отвечает исправно и
показывает вердикт по каждому вопросу. Ученик видит рабочую викторину ровно до
той секунды, когда она должна засчитаться.

## Почему прогон оставался зелёным

Тесты на `/submit` для викторины были, и все посылали `{"answers": [...]}` —
форму из схемы, а не ту, что уходит из браузера. Форму, которой шлёт клиент, не
проверял никто.

`test_submit_exercise` в `test_exercises.py` формально трогает этот маршрут, но
допускает `200, 422, 400` — упасть он не мог.

## Требования

- **FR-001.** Ответ на викторину в том виде, в каком его шлёт V2-рендерер,
  оценивается и сохраняется. Верные ответы дают 100 и `passed`.
- **FR-002.** Конверт именно разворачивается, а не проглатывается. Читатель,
  возвращающий на эту форму пустой список, тоже ответил бы 200 — и поставил бы
  ноль за верную работу.
- **FR-003.** Отправка вообще без ответов — это ноль, а не 500.
- **FR-004.** В сохранённой попытке лежат ответы ученика. Учитель открывает
  разбор и видит работу, а не пустой экран.
- **FR-005.** `/check` и `/submit` разбирают тело **одним** читателем.
  Разъехались они потому, что разбирали его порознь.
- **FR-006.** У каждого требования есть тест, который падает на неисправленном
  коде.

## Что осталось незакрытым — намеренно

**Клиент не правится.** Форма `{"interactive_answers": {...}}` — общая для всех
типов V2, и её понимает `/check`. Переименовать поле на клиенте значило бы
сломать вкладки, где уже загружен старый JS: они продолжат слать прежнюю форму
ещё сутки после выкладки. Принимать обе формы должен сервер.

**Сплошной сверки `.get(ключ, умолчание)` по необязательным полям схем не
делалось.** Ловушка общая: у любого поля с `= None` в схеме умолчание в `.get`
недостижимо. Соседний `_submit_interactive` написан верно
(`data.get("interactive_answers") or data.get("answers", {})`), остальные
обработчики не проверялись. Это отдельная работа, и делать её стоит линтером, а
не глазами.

**Модуль `assessments` не затронут.** Его `submit_quiz` берёт `answers:
list[dict]` отдельным аргументом из своей схемы, где поле обязательное. Другой
маршрут, другая форма, той же поломки там нет.

**Сколько работ потеряно, из базы не восстановить.** Попытка не создавалась
вовсе — 500 приходил до `db.add`, — поэтому в отчётах нет ни нулей, ни
проваленных попыток. Ученик просто не числится проходившим викторину.

## Как проверено

1. **Поломка воспроизведена тестом до правки** — прогон падал ровно тем
   `TypeError` из Sentry.
2. **Положительный контроль в том же файле.** Тест на форму из схемы проходил и
   до правки: без него «нет 500» не доказывало бы, что хоть что-то оценивается.
3. **Обратный контроль.** Неверные ответы в том же конверте дают ноль — читатель,
   молча возвращающий пустой список, этот тест не прошёл бы.
4. **Прогон бэкенда целиком** на Postgres 16 с `pgvector`, плюс `ruff check`,
   который гоняет CI.
