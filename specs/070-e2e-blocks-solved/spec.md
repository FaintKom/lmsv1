# Спецификация: E2E решает блоки урока до «пройдено»

**Ветка**: `test/e2e-solved-blocks`

**Создано**: 2026-09-02

**Статус**: Черновик

**Ввод**: «E2E-тесты решают каждый тип блока урока до вердикта „пройдено“, а не
только проверяют, что блок отрисовался. После specs/027 (#416)
`all-content-types.spec.ts` проверяет лишь рендер блоков matching, ordering,
categorize, fill_blanks, true_false, quiz, code_challenge, file_upload; никто в
браузере не решает их до „пройдено“ и не проверяет, что урок засчитан. Файл к
тому же выключен на PR через `E2E_SKIP_EXTERNAL` из-за живого YouTube. Нужно:
для каждого решаемого типа тест вводит верный ответ через UI, получает вердикт
„пройдено“ от сервера и видит, что прогресс урока вырос; неверный ответ даёт
„не пройдено“ хотя бы для одного типа как положительный контроль; тест должен
быть гейтом на PR, значит без обращений к внешним сайтам.»

## Откуда взялось

Спека 027 обещала: «покрытие E2E по типам сохраняется, но идёт через блоки»
(FR-004, SC-003). Обещание выполнено наполовину. Прежний обход умел решать
задание и видеть «пройдено»; новый только проверяет, что блок нарисовался: пары
matching на экране, редактор кода смонтирован, поле для файла есть. Сам файл
это признаёт в шапке: «What it does NOT prove, and did before: that solving
each one is graded correctly».

Цена этой дыры уже известна. Ручной прогон 2026-08-23 нашёл, что урок из
упражнений невозможно закончить (specs/050): ученик видел «Got it!», а
прогресс курса стоял на месте. Ни один автоматический тест этого не поймал,
потому что ни один не решал задание в браузере до конца. То же самое с #479:
вопрос из редактора доезжал до ученика пустым, и обход не заметил, потому что
проверял, что блок есть, а не что его можно решить.

Кроме того, обход не гейт. На pull request он выключен флагом
`E2E_SKIP_EXTERNAL`, потому что блоки видео и презентации ходят на живые
youtube.com и docs.google.com. Значит, даже те проверки, что в нём есть, на PR
не запускаются.

## Сценарии

### Сценарий 1 — Ученик решает блок и получает «пройдено» (P1)

Для каждого из восьми типов блока, которые сегодня есть в обходе, тест в роли
ученика открывает урок с этим блоком, вводит верный ответ теми же органами
управления, что и живой ученик, отправляет его и видит вердикт «пройдено».
Вердикт сверяется не с надписью на экране, а с тем, что сервер записал в
сдачу: сдача существует, она успешна.

Типы: quiz, true_false, matching, ordering, categorize, fill_blanks,
code_challenge, file_upload.

Для `file_upload` «пройдено» значит иное: ответ не проверяется автоматически,
и вердикт ученика — «сдано, ждёт проверки учителя». Тест проверяет, что файл
дошёл до сервера и учитель видит сдачу в своём списке на проверку.

**Почему P1**: это и есть обещание спеки 027, не выполненное до сих пор. Всё
остальное в этой спеке служит ему.

**Независимая проверка**: любой один тип, доведённый до «пройдено», уже
закрывает дыру для этого типа.

**Приёмка**:

1. **Дано** урок с одним блоком типа T, **когда** ученик вводит верный ответ и
   отправляет его, **тогда** на экране вердикт «пройдено», а на сервере у
   этого ученика по этому заданию есть успешная сдача.
2. **Дано** блок code_challenge с тестовыми случаями, **когда** ученик вводит
   решение, проходящее все случаи, **тогда** вердикт «все тесты пройдены» и
   успешная сдача на сервере.
3. **Дано** блок file_upload, **когда** ученик прикладывает файл и
   отправляет, **тогда** сдача видна учителю в списке на проверку.

### Сценарий 2 — Урок засчитан после решения (P1)

После успешной сдачи всех заданий урока ученик видит, что урок закрыт, а
прогресс курса вырос. Это правило specs/050: урок с заданиями закрывается
решением, а не кнопкой.

**Почему P1**: именно это сломалось 2026-08-23, и именно этого не видит
никакой тест до сих пор.

**Независимая проверка**: один урок с одним заданием; до сдачи прогресс
курса ниже, после сдачи выше и урок отмечен пройденным.

**Приёмка**:

1. **Дано** курс с уроком из одного задания и прогресс курса 0 %, **когда**
   ученик решает задание верно, **тогда** урок отмечен пройденным и прогресс
   курса больше нуля.
2. **Дано** урок с двумя заданиями, **когда** ученик решил одно, **тогда**
   урок ещё не закрыт; **когда** решил второе, **тогда** закрыт.

---

### Сценарий 3 — Неверный ответ даёт «не пройдено» (P1)

Хотя бы для одного типа тест вводит неверный ответ и видит «не пройдено»: на
экране предложение попробовать снова, на сервере сдача без успеха, урок не
закрыт.

**Почему P1**: без этого сценарий 1 не способен упасть. Проверка, которая
принимает любой ответ за верный, зелёная всегда (конституция, принцип II).

**Независимая проверка**: один тип, один неверный ответ.

**Приёмка**:

1. **Дано** блок quiz, **когда** ученик выбирает неверный вариант и
   отправляет, **тогда** вердикт «не пройдено», сдача на сервере неуспешна,
   урок не закрыт.

---

### Сценарий 4 — Обход стал гейтом на pull request (P2)

Обход запускается на каждом pull request и блокирует слияние при падении. Для
этого он не обращается ни к одному узлу вне стенда: ни к YouTube, ни к
Google, ни к иным внешним адресам.

**Почему P2**: без гейта сценарии 1–3 проверяют только того, кто вспомнил их
запустить. Но сами проверки ценны и до включения в гейт.

**Независимая проверка**: прогон в режиме pull request с закрытой внешней
сетью проходит все тесты обхода.

**Приёмка**:

1. **Дано** pull request, **когда** запускается набор E2E, **тогда** обход
   блоков входит в него и его падение делает проверку красной.
2. **Дано** стенд без доступа во внешнюю сеть, **когда** обход запускается,
   **тогда** ни один тест не ждёт внешний ресурс и не падает по его
   недоступности.

---

### Крайние случаи

- Задание с несколькими попытками: тест проверяет вердикт первой попытки, а
  не «когда-нибудь пройдено».
- Ответ, верный по смыслу, но отличающийся порядком (matching, categorize):
  вердикт зависит только от правильности пар и групп, не от порядка их
  ввода.
- Блок code_challenge при недоступной песочнице: тест должен упасть с
  понятной причиной, а не зависнуть на ожидании вердикта.
- Блок видео и презентации в гейте: их проверка «нарисовался» не должна
  зависеть от внешнего хостинга. Либо источник живёт внутри стенда, либо
  проверка внешних встраиваний остаётся вне гейта, а решаемые блоки в гейт
  входят в любом случае.
- Повторный прогон на том же стенде: данные предыдущего прогона не должны
  делать тест зелёным заранее (например, урок, уже закрытый прошлым
  запуском). Каждый прогон заводит свои курс и уроки и убирает их за собой.

## Требования

### Функциональные

- **FR-001**: Для каждого из восьми типов (quiz, true_false, matching,
  ordering, categorize, fill_blanks, code_challenge, file_upload) существует
  тест, который в роли ученика вводит ответ через интерфейс и отправляет его.
- **FR-002**: Для семи автоматически проверяемых типов тест утверждает
  вердикт «пройдено» по данным сервера, а не только по надписи на экране.
- **FR-003**: Для file_upload тест утверждает, что сдача дошла до сервера и
  видна учителю на проверке.
- **FR-004**: Хотя бы для одного типа тест с неверным ответом утверждает
  «не пройдено» по данным сервера и незакрытый урок.
- **FR-005**: Тест утверждает, что после успешной сдачи всех заданий урока
  урок отмечен пройденным и прогресс курса вырос.
- **FR-006**: Каждый тест решения способен упасть: при подмене верного
  ответа неверным он краснеет. Это демонстрируется при разработке и
  фиксируется в описании pull request (конституция, принцип II).
- **FR-007**: Обход не обращается к узлам вне стенда и запускается на pull
  request как блокирующая проверка.
- **FR-008**: Ответы вводятся теми же органами управления, что видит ученик.
  Подстановка ответа в обход интерфейса (прямой вызов сервера вместо клика)
  не считается решением блока.
- **FR-009**: Проверка «блок нарисовался» для видео и презентаций сохраняется,
  но не мешает гейту: либо без внешней сети, либо вне гейта.
- **FR-010**: Каждый прогон создаёт свои данные и убирает их за собой;
  повторный прогон на том же стенде не опирается на следы предыдущего.

### Ключевые сущности

- **Блок урока**: единица содержимого на странице урока; решаемый блок
  ссылается на задание.
- **Сдача**: ответ ученика на задание с вердиктом сервера: успешна или нет.
- **Прогресс урока и курса**: урок закрыт, когда успешны все его задания;
  процент курса пересчитывается из закрытых уроков.

## Критерии успеха

- **SC-001**: Восемь типов блока доведены в браузере до вердикта сервера;
  ноль типов из списка проверяются только на отрисовку.
- **SC-002**: Хотя бы один тест на «не пройдено» и один на закрытие урока
  есть и зелёные.
- **SC-003**: При намеренной подмене верного ответа неверным каждый тест
  решения краснеет; результат этой проверки записан в pull request.
- **SC-004**: Обход входит в проверку pull request и проходит без доступа во
  внешнюю сеть.
- **SC-005**: Дефекты вида specs/050 (урок не закрывается) и #479 (задание
  доезжает пустым) ловятся обходом: прогон на коммите до их исправления
  красный.

## Допущения

- В этой спеке восемь типов: те, что сегодня в обходе и перечислены во
  вводе. Остальные девятнадцать решаемых типов (языковые, математические,
  игровые, SCORM, flashcards, кроссворды и прочие) остаются отдельной
  работой. Часть из них уже решается в браузере своими сценариями
  (robot_2d, world_3d), часть проверяется только на «не 5xx» в
  `lifecycle.spec.ts`.
- «Вердикт сервера» читается через существующие ручки чтения сдач и
  прогресса; новых ручек для теста не заводится.
- Песочница для code_challenge на стенде поднята и используется как есть.
- Оценка file_upload учителем не входит: это уже покрыто сценарием домашних
  заданий (`teacher-homework.spec.ts`), здесь важна только доставка сдачи.
- Верные ответы известны тесту, потому что он сам создаёт задания в роли
  учителя. Это не нарушает принцип III конституции: ключ у автора задания, а
  не у ученика.
