# Implementation Plan: Мёртвый ключ меню в настройках школы

**Branch**: `claude/magical-burnell-40a406` | **Date**: 2026-08-22 | **Spec**: [spec.md](./spec.md)

**Input**: Feature specification from `/specs/039-dead-menu-visibility-key/spec.md`

## Summary

Один `UPDATE` в миграции Alembic и один тест на бэкенде.

Миграция снимает ключ `meetings` с карты видимости меню оператором `-` и ставит
результат обратно через `jsonb_set`. Условие в `WHERE` отбирает только те строки,
где карта — объект и ключ в ней есть; на втором прогоне таких строк ноль, и
повторная безопасность получается из самого условия, а не из отдельной проверки.

Тест закрепляет контракт, на котором держится вторая половина спеки: сервер
кладёт присланную карту поверх старой целиком, а не сливает по ключам. Пока это
так, форма настроек стирает мёртвые ключи любым сохранением; если кто-нибудь
«улучшит» слияние до глубокого, мусор станет несмываемым — тест упадёт раньше,
чем это доедет до прода.

Кода на фронтенде не прибавляется: `MENU_ITEM_KEYS` уже не знает `meetings`
(вместо него `live`), и форма собирает карту только из этого списка.

## Technical Context

**Language/Version**: Python 3.12

**Primary Dependencies**: Alembic, SQLAlchemy 2 async, FastAPI

**Storage**: PostgreSQL 16 — `organizations.settings` (JSONB), ключ
`menu_visibility`. Схема не меняется: правятся данные внутри колонки.

**Testing**: pytest против настоящего PostgreSQL (`docker compose up -d db`,
образ `pgvector/pgvector:pg16`)

**Target Platform**: веб, тот же, что и весь продукт

**Project Type**: web application — правка целиком в `backend/`

**Constraints**: миграция повторно-безопасна; данные едут только через GitHub;
прод только на чтение

**Scale/Scope**: две школы в проде, по одному лишнему ключу у каждой

## Constitution Check

- **Изоляция арендаторов**: миграция идёт по всем школам одинаково и ничего между
  ними не переносит. Прав доступа не касается.
- **Тесты, которые способны упасть**: новый тест кладёт в карту посторонний ключ,
  сохраняет настройки и требует, чтобы ключа не стало. На глубоком слиянии он
  красный. Проверка не проходит бесплатно — есть и положительный контроль: в той
  же карте известный ключ со значением `false` обязан пережить сохранение.
- **Серверная проверка ответов**: не относится.

## Решения

**Почему `jsonb_exists(...)`, а не оператор `?`.** Знак вопроса внутри SQL —
плейсхолдер параметра для части драйверов, и строка с ним ломается не там, где
её писали. Функция делает ровно то же и не зависит от того, чем сегодня ходят
в базу.

**Почему условие, а не безусловный `UPDATE`.** Безусловный переписал бы каждую
строку таблицы при каждом прогоне: та же карта, новая версия ряда. Условие
оставляет счётчик изменённых строк честным — по нему и проверяется SC-003.

**Почему не общая уборка по списку разрешённых ключей.** Замер по проду показал
один лишний ключ, а не класс проблемы. Список разрешённых пришлось бы держать
второй копией на Python рядом с `MENU_ITEM_KEYS` на TypeScript, и он разошёлся бы
с ней на следующем же переименовании — как разошёлся `meetings`. Убираем то, что
есть.

**Откат — пустой.** Миграция вниз не возвращает ключ. Восстанавливать мусор
незачем, а притворяться, что откат полный, — врать в коде.

## Проверка

1. `pytest backend/tests/test_admin.py -k settings` — зелёный, и новый тест
   красный на подменённом на глубокое слияние сервере.
2. `alembic upgrade head` на локальной базе с посеянным ключом: ключа нет,
   остальные на месте.
3. `alembic upgrade head` второй раз: `UPDATE 0`.
4. После выката — один запрос к проду на чтение: ключей `meetings` ноль.
