# Contract: `GET /api/v1/auth/me`

Единственный изменённый контракт. Меняется добавлением поля; ничего
не переименовывается и не удаляется.

## Было

```jsonc
{
  "id": "…", "email": "…", "role": "teacher", "org_id": "…",
  "org_branding": {
    "logo_url": null,
    "primary_color": "#22c55e",
    "secondary_color": "#3b82f6",
    "display_name": "Green Valley School"
  }
}
```

## Стало

```jsonc
{
  "id": "…", "email": "…", "role": "teacher", "org_id": "…",
  "org_branding": {
    "logo_url": null,
    "primary_color": "#22c55e",
    "secondary_color": "#3b82f6",
    "display_name": "Green Valley School",
    "menu_visibility": { "gradebook": false, "calendar": true }
  }
}
```

## Правила

- **Кому.** Любой аутентифицированный пользователь. Организация берётся из
  токена; параметра с идентификатором организации у эндпоинта нет и не
  появляется.
- **Что внутри.** Карта из `organizations.settings.menu_visibility`: ключ
  пункта меню → показывать или нет. Ключи не фильтруются и не дополняются —
  что школа сохранила, то и приезжает.
- **Если карты нет.** Приезжает `{}`. Не `null` и не отсутствующее поле:
  `null` в настройках старых школ читается как пустая карта.
- **Умолчание.** Ключ, которого в карте нет, означает «показывать». Это
  правило живёт на клиенте и не меняется.
- **Совместимость.** Поле добавляется, поэтому старый клиент его игнорирует.
  Новый клиент читает через `?.`, чтобы пережить окно выката, когда фронтенд
  уже новый, а бэкенд ещё старый.

## Чего контракт не меняет

`PUT /api/v1/admin/organizations/{org_id}` — запись настроек — остаётся
за администратором, с той же проверкой роли.

`GET /api/v1/admin/organizations/{org_id}` — чтение настроек целиком —
остаётся за администратором. Страница `/admin/settings` продолжает ходить
туда: ей нужны все настройки, а не одна карта.
